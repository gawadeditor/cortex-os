# Asset & Archive Governance Design

**Phase:** B5.12  
**Depends on:** B5.5 (Review System), B5.7 (Learning Module), B5.8 (Analytics Layer), B5.11 (Budget & Cost Governance), B4.75 (Channel Profile), B7 (Run OS)  
**Feeds into:** Run OS (archive reuse lookup), Learning Module (archive signals), Budget & Cost Governance (storage costs), Dashboard (asset visibility)

---

## 1. Purpose

The Asset & Archive Governance layer manages the lifecycle of all production assets generated by Factory OS — from creation through verification, publication, archiving, and optional purge. It governs where assets live, how long they are kept, when they can be reused, and how their quality is maintained across time.

The two core functions:

**Governance:** Enforcing the archive policy defined in each Channel Profile. Determining when assets move between storage tiers, when they can be reused, and when they can be purged.

**Reuse:** Before generating a new asset, the pipeline can look up whether an equivalent asset already exists in the archive. A cache hit avoids the generation cost entirely.

### 1.1 What Asset Governance does not own

| Concern | Owner |
|---|---|
| Executing asset generation | Production agents (VPD, Thumbnail Director, ElevenLabs, etc.) |
| Storing the asset bytes at the infrastructure level | Storage backend (S3, GCS, local disk) |
| Recording gate verdicts against assets | Acceptance Audit / Review System |
| Deciding which assets to generate | Run OS / Agent Director |
| Recommending cost optimizations via archive reuse | Learning Module |

Asset Governance records asset metadata, tracks lifecycle, resolves archive lookups, and enforces policy. The storage backend stores the bytes. These are separate responsibilities.

## 2. Asset Types

Twelve asset types are produced across the production pipeline. Each type has a distinct size profile, lifecycle behavior, and reuse eligibility.

| Asset type | Stage produced | Typical size | Reuse eligible | Notes |
|---|---|---|---|---|
| `script` | Script Engine | < 50 KB | No | Episode-specific text; never reused across episodes |
| `visual_plan` | Visual Package Director | < 100 KB | No | Scene planning output; episode-specific |
| `scene_image` | Image generation (MUAPI/Stability) | 1–5 MB each | Yes | Reusable if scene prompt + style descriptor match |
| `scene_video` | Video generation (Seedance/Runway) | 50–500 MB each | Yes | Reusable if scene prompt + motion parameters match |
| `narration_audio` | ElevenLabs | 10–80 MB | No | Episode-specific narration; not reusable |
| `background_music` | Music API or static library | 5–30 MB | Yes | Reusable across episodes in same channel (same mood/tempo) |
| `thumbnail` | Thumbnail Director | < 2 MB | No | Episode-specific; not reused |
| `captions` | Caption generation | < 100 KB | No | Episode-specific timing |
| `metadata_package` | Metadata agent | < 50 KB | No | Episode-specific titles/descriptions |
| `composite_video` | Assembly stage | 1–10 GB | No | Final assembled episode video; not reused but retained |
| `short_form_clip` | Short form extraction | 50–500 MB | Conditional | Derived from composite_video; may be reused as scene reference |
| `run_snapshot` | Run OS | < 5 MB | No | Execution state and config; never reused |

### 2.1 Reuse eligibility criteria

An asset is eligible for reuse if:
1. Its type is marked reuse-eligible (above)
2. Its `quality_status = verified` (it passed quality gates at the time it was produced, OR it has been re-evaluated against current standards and still passes)
3. It is within its retention window (not expired)
4. Its generating parameters sufficiently match the new request's parameters (similarity threshold met)
5. It belongs to the same factory (cross-factory reuse is never permitted)

## 3. Asset Lifecycle

### 3.1 Lifecycle states

```
produced
  → verified               (gate passed, or quality check confirmed post-hoc)
  → in_use                 (referenced by an active run or published episode)
  → hot_retained           (run completed; within retention window; on primary storage)
  → warm_archived          (moved to lower-cost warm storage after compress_after_days)
  → cold_archived          (moved to deep archive storage — high latency to access)
  → purged                 (deleted from all storage; record metadata retained permanently)
```

An asset can regress from `verified` to `needs_reverification` if quality standards change — see §7.

### 3.2 State transition rules

| Transition | Trigger |
|---|---|
| `produced` → `verified` | Acceptance Audit gate pass, or BGA/QA post-hoc check |
| `produced` → `failed` | Gate failure; asset is not archived; may be deleted immediately |
| `verified` → `in_use` | Referenced by a live run or published episode |
| `in_use` → `hot_retained` | Run completes and the episode is published |
| `hot_retained` → `warm_archived` | `compress_after_days` threshold from Channel Profile |
| `warm_archived` → `cold_archived` | Optional — configurable per channel for high-volume archive |
| `hot_retained` → `purged` | `retention_days` exceeded (if set), OR operator-initiated purge with confirmation |
| `warm_archived` → `purged` | Same as above, from warm tier |
| `cold_archived` → `purged` | Same as above, from cold tier |
| `verified` → `needs_reverification` | Quality standards updated since this asset was produced |

`purged` is terminal. The asset bytes are deleted, but the `AssetRecord` metadata is retained permanently in the asset registry. Purged assets appear in the registry with `storage_status: purged` and no recoverable bytes.

### 3.3 Failed asset handling

Assets that fail quality gates (`produced` → `failed`) are handled by the channel's archive policy:

- If `retain_raw_assets = false`: failed assets are deleted immediately after the gate failure is recorded
- If `retain_raw_assets = true`: failed assets are retained in `hot_retained` state with `quality_status: failed` — available for debugging but not for archive reuse
- Failed assets in `hot_retained` state follow the same retention_days policy as verified assets

## 4. Storage Tiers

### 4.1 Tier definitions

| Tier | Access latency | Cost profile | Use case |
|---|---|---|---|
| **Hot** | Immediate (< 1 second) | Highest per-GB | Active production: assets within compress_after_days window; in-use by current runs |
| **Warm** | Seconds to minutes | Moderate (≈ 40% of hot) | Archive reuse candidates; assets past compress_after_days |
| **Cold** | Minutes to hours | Lowest (≈ 10% of hot) | Deep archive; rarely accessed; asset compliance retention |
| **Purged** | Not accessible | Zero | Deleted; metadata record retained |

### 4.2 Tier assignment policy

Tier assignment follows the Channel Profile's `archive_policy`:

```
// From Channel Profile (B4.75 §4):
retain_raw_assets:      boolean     // keep scene_image, scene_video, narration_audio
retain_intermediate:    boolean     // keep script, visual_plan, run_snapshot
retention_days:         int | null  // days to keep before purge; null = indefinite
compress_after_days:    int | null  // days before moving to warm tier; null = stay hot forever
delete_on_archive:      boolean     // if channel archived, purge assets after retention_days
```

**Tier assignment logic per asset:**

```
if asset.age_days < compress_after_days (or compress_after_days is null):
  tier = hot

if asset.age_days >= compress_after_days:
  tier = warm

if retention_days is set and asset.age_days >= retention_days:
  tier = purged (scheduled for deletion)

if channel is archived and delete_on_archive = true:
  tier = purged (scheduled for deletion, after retention_days)
```

### 4.3 Tier movement operations

Tier movements are scheduled by the Asset Governance layer and executed by the storage backend:

- `hot → warm`: move bytes to warm-tier storage; update asset tier and storage URI
- `warm → cold`: move bytes to cold-tier; update asset tier and storage URI
- `any → purged`: delete bytes from storage; update asset record with `storage_status: purged`, `purged_at`, `purge_reason`

Tier movements are logged in the asset audit trail. The asset's storage URI changes after each movement; the Asset Governance layer maintains the current URI so callers always resolve correctly.

## 5. Archive Reuse

### 5.1 Purpose

When the production pipeline needs a specific type of asset, it first queries the archive for an existing asset that is equivalent to the one it would generate. A cache hit:
- Eliminates the generation cost
- Eliminates the generation latency
- Reduces provider API usage (reducing provider budget pressure)

The Learning Module tracks the archive hit rate as a learning signal (cost efficiency domain).

### 5.2 Archive lookup interface

The Run OS calls `lookup_archive_asset()` before initiating any reuse-eligible asset generation task:

```
lookup_archive_asset(
  channel_id,
  asset_type,
  lookup_parameters     // type-specific parameters used to assess equivalence
) → ArchiveLookupResult
```

**Lookup parameters per asset type:**

| Asset type | Lookup parameters |
|---|---|
| `scene_image` | `style_descriptor`, `scene_description_hash`, `color_palette_id`, `aspect_ratio` |
| `scene_video` | `style_descriptor`, `scene_description_hash`, `motion_style`, `duration_seconds`, `color_palette_id` |
| `background_music` | `mood`, `tempo_bpm_range`, `duration_range_seconds`, `instrument_profile` |

**Lookup result:**

```
ArchiveLookupResult {
  hit:              boolean
  asset_id:         string | null
  asset_uri:        string | null       // resolved storage URI
  asset_tier:       string | null       // hot | warm | cold
  similarity_score: float | null        // 0.0–1.0; how well the asset matches parameters
  quality_status:   string | null       // verified | needs_reverification
  retrieval_latency_estimate: int | null // estimated seconds to retrieve (cold tier: longer)
}
```

### 5.3 Similarity threshold

Archive reuse is only approved when `similarity_score ≥ threshold`. Thresholds per asset type:

| Asset type | Minimum similarity | Rationale |
|---|---|---|
| `scene_image` | 0.85 | Image generation is deterministic enough to allow high reuse with close parameter matching |
| `scene_video` | 0.90 | Video is more sensitive to motion style differences |
| `background_music` | 0.80 | Music can tolerate more variation if mood and tempo match |

If no asset meets the similarity threshold, `hit = false` and the pipeline generates a new asset.

### 5.4 Quality recheck for archived assets

Before using a retrieved archive asset, the Asset Governance layer checks whether the asset requires reverification:

- If `quality_status = verified` and the asset was verified after the channel's current BGA version and quality thresholds were set: **proceed**
- If `quality_status = needs_reverification`: **do not reuse without reverification**
- Reverification: BGA and QA agent evaluate the archived asset against current standards. If it passes: `quality_status → verified`, timestamp updated. If it fails: `quality_status → failed`, asset excluded from reuse.

Reverification is triggered automatically when an asset is retrieved from the archive and its `verified_at` timestamp is older than the most recent BGA configuration update date for the channel.

### 5.5 Cold tier retrieval latency

If the best available archive match is in cold storage, the Asset Governance layer informs the Run OS of the estimated retrieval latency before the run commits to using the archived asset. The run coordinator decides:

- If the latency is acceptable (< 30 minutes), retrieve from cold and use the archive asset
- If the latency exceeds the run's time constraints, generate a new asset instead

The run coordinator never blocks on cold retrieval without explicit operator configuration permitting it.

## 6. Archive Run

The `archive_run` is a scheduled maintenance run type (B7 Run OS §4.4) that performs three functions:

1. **Index update:** Scans recent episode outputs and indexes them for archive reuse eligibility.
2. **Quality drift check:** Re-evaluates a sample of archived assets against current quality standards to detect which ones have become `needs_reverification`.
3. **Tier migration:** Identifies assets that have aged past their `compress_after_days` threshold and schedules them for warm-tier migration. Identifies assets that have exceeded `retention_days` and schedules them for purge.

The archive_run runs weekly by default, or on-demand after a major BGA configuration update.

### 6.1 Archive run outputs

| Output | Destination |
|---|---|
| Updated asset index (new episodes indexed for reuse) | Asset Registry |
| Quality drift signals | OIS (via Asset Governance) → Learning Module |
| Tier migration schedule | Storage backend job queue |
| Archive hit rate report | Budget Governance (storage cost trend), Learning Module |
| Reverification queue | Asset Governance (list of assets needing BGA re-check) |

## 7. Quality Governance

### 7.1 Quality drift problem

An asset that was `verified` two months ago was evaluated against the BGA threshold and standards in effect at that time. If the channel's brand rules have been updated (e.g., the color palette was adjusted, the forbidden visual elements list was extended), the asset may no longer meet current standards — even though it was verified at the time of production.

Asset Governance tracks this through two mechanisms:

**BGA configuration version tracking:** Every VerificationRecord stores the `bga_config_version` at the time of verification. When the channel's BGA configuration is updated (new BGA threshold, new brand rules), all archived assets with an older `bga_config_version` are marked `needs_reverification`.

**Sample-based quality drift detection:** The archive_run evaluates a random sample of archived assets (configurable sample rate, default 10%) against current standards. If the sample shows a quality drift rate above 20%, all assets in that asset_type / channel combination are marked `needs_reverification`.

### 7.2 Reverification queue

Assets needing reverification are placed in a `ReverificationQueue`. They are not used for archive reuse until reverification is complete. The reverification queue is processed by the archive_run (for batch evaluation) or triggered immediately when a specific asset is requested for reuse (on-demand reverification).

On-demand reverification: when `lookup_archive_asset()` returns an asset with `quality_status = needs_reverification`, the Asset Governance layer initiates immediate reverification if the archive run has not yet processed this asset. If the reverification completes within the task's waiting tolerance (configurable, default 60 seconds), the result is used. Otherwise, the pipeline generates a new asset.

## 8. Asset Purge Governance

Purging assets is the permanent deletion of stored bytes. Purge is irreversible.

### 8.1 Purge eligibility

An asset is eligible for purge when:
- `retention_days` is set AND `asset.age_days ≥ retention_days`, OR
- The channel is being archived AND `delete_on_archive = true` in the Channel Profile, AND `retention_days` has elapsed

Assets in the following states are never automatically purged regardless of retention_days:
- `in_use` (actively referenced by a running or published episode)
- `needs_reverification` (held for quality evaluation — purging would destroy the evaluation subject)

### 8.2 Purge execution

Purge is not executed immediately when an asset becomes eligible. The Asset Governance layer runs a `purge_evaluation` step:

1. Identify all purge-eligible assets
2. For each eligible asset, confirm it is not `in_use`
3. Confirm that the episode it belongs to has `published_at` set (not pending publication)
4. Record the purge intent in the `AssetPurgeQueue`
5. Execute purge on the next archive_run

A 48-hour grace period applies between when an asset enters the purge queue and when bytes are deleted. This gives the operator time to pause a purge if they realize it was misconfigured.

### 8.3 Operator-initiated purge

Admin+ can initiate a purge of specific assets or all assets for a channel through the dashboard. This is a **Dangerous action** (two-step confirmation with intent token).

Operator-initiated purge is the only way to purge assets before their `retention_days` has elapsed. The reason for early purge is required and stored in the audit trail.

### 8.4 What is never purged

- `AssetRecord` metadata (the record that an asset existed is permanent — the bytes can be gone but the record remains)
- `VerificationRecord` records (gate verdicts against assets are immutable)
- `run_snapshot` assets (retained indefinitely for run reproducibility audit)
- Assets for episodes that have not yet completed their platform analytics stabilization window (purging before analytics can be linked breaks the learning signal chain)

## 9. Cross-Channel Isolation

### 9.1 Channel scope

Every asset is tagged with `channel_id` at creation. Archive lookups are scoped to the requesting channel by default:

```
lookup_archive_asset(channel_id, ...) → only searches assets where asset.channel_id = channel_id
```

### 9.2 Cross-channel reuse

Cross-channel asset reuse is possible only if:
- `cross_channel_learning = true` in the factory's Channel settings for both channels
- Both channels share the same factory (`factory_id` matches)
- The asset's channel has explicitly enabled `allow_cross_channel_reuse = true` in archive settings

When cross-channel reuse is enabled, the archive lookup extends to assets from enabled source channels. The reused asset is attributed to the source channel for provenance tracking — it is not re-attributed to the requesting channel.

Cross-channel reuse is disabled by default. For client channels, cross-channel reuse is never permitted unless the factory admin explicitly enables it and both client contracts allow it.

### 9.3 Client isolation

Assets produced for a client channel belong to that client's production scope. They are not visible to, and cannot be reused by, any other client's channels. This applies even when the factory manages multiple clients under the same factory instance.

## 10. Integration Points

### 10.1 Run OS → Asset Governance

The Run OS calls Asset Governance at two points:

**Before asset generation (archive lookup):**
```
lookup_archive_asset(channel_id, asset_type, lookup_parameters)
→ ArchiveLookupResult
```

**After asset generation (asset registration):**
```
register_asset(channel_id, episode_id, run_id, task_id, asset_type, storage_uri,
               file_size_bytes, generating_parameters)
→ AssetRecord
```

### 10.2 Acceptance Audit → Asset Governance

After gate verdicts are recorded by the Acceptance Audit, it calls Asset Governance to update asset quality status:

```
record_asset_verification(asset_id, gate_type, verdict, bga_config_version, verified_at)
→ VerificationRecord
```

This transitions the asset from `produced` to `verified` or `failed`.

### 10.3 Learning Module → Asset Governance (read)

The Learning Module reads archive metrics for the `cost_efficiency` domain:

```
get_archive_metrics(channel_id, window_days)
→ {
    archive_hit_rate,         // hits / (hits + misses) for lookup attempts
    archive_miss_rate,
    cost_saved_usd,           // estimated cost saved from archive hits
    quality_drift_rate,       // % of sampled archived assets needing reverification
    purge_rate_by_type,       // % of each asset type purged in the window
    cold_tier_retrieval_count // how often cold retrieval was used (latency risk indicator)
  }
```

Archive hit rate is a direct cost efficiency signal. If hit rate is low for a channel with many reuse-eligible assets, the Learning Module may generate a `workflow_recommendation` suggesting adjustments to scene prompting or visual planning that would improve parameter consistency and archive reuse.

### 10.4 Budget & Cost Governance → Asset Governance

Storage cost is tracked per asset tier. Asset Governance reports storage consumption to Budget Governance:

```
get_storage_cost_summary(channel_id, period_start, period_end)
→ {
    hot_storage_gb,   hot_storage_cost_usd,
    warm_storage_gb,  warm_storage_cost_usd,
    cold_storage_gb,  cold_storage_cost_usd,
    total_storage_cost_usd
  }
```

Storage costs are recorded as `storage_cost` category in the Cost Ledger via `record_cost()`.

### 10.5 Publishing Pipeline → Asset Governance

When an episode is published, the Publishing Pipeline signals Asset Governance to mark all assets for that episode as `in_use`:

```
mark_episode_assets_published(episode_id)
→ { assets_updated: int }
```

This prevents assets for published episodes from being purged before their retention window.

Called by: Run OS (after each asset is produced).

```
register_asset(
  channel_id,
  episode_id,
  run_id,
  task_id,
  asset_type,
  storage_uri,
  file_size_bytes,
  content_hash,

### 13.2 lookup_archive_asset()

Called by: Run OS (before initiating reuse-eligible asset generation).

```

  lookup_parameters,

### 13.3 record_asset_verification()

Called by: Acceptance Audit.

## 14. Local-First and SaaS Readiness

### 14.1 Local-first V1

In V1, assets are stored on local disk or a locally-configured cloud storage account (S3-compatible bucket). The storage URI format is configurable (e.g., `file:///factory/assets/`, `s3://bucket/path/`). The Asset Governance layer is storage-backend-agnostic — it stores the URI and delegates byte operations to the configured backend.

Storage tier migration (hot → warm → cold) requires the storage backend to support multiple storage classes. In V1 with local disk, tier migration is simulated by moving files between directories (`/hot/`, `/warm/`, `/cold/`). With S3, tiers map to S3 storage classes (Standard → Standard-IA → Glacier).

Archive reuse lookup latency on cold tier: if using local disk, "cold" is the same disk — no latency penalty. With Glacier, retrieval can take hours — the Asset Governance layer must account for this in lookup results.

### 14.2 SaaS readiness

**Per-factory asset isolation:** Every AssetRecord is scoped to `factory_id`. Assets cannot be accessed across factory boundaries. The storage backend uses per-factory key prefixes (or separate buckets) to enforce isolation at the byte level, not just at the metadata level.

**Client channel isolation:** Within a multi-client factory, client channel assets are in sub-scopes labeled by `channel_id`. Asset lookup and purge operations always require `channel_id` — it is not possible to query all assets across clients.

**Tenant storage accounting:** For SaaS billing, storage cost by factory (and optionally by channel, for pass-through billing to clients) is computed from `get_storage_cost_summary()`.

**Audit trail:** Every asset lifecycle state transition is logged: who triggered it, when, why, and what the previous and new states were. Asset purge events are logged permanently even after the asset bytes are gone. This audit is per-factory and immutable.

## 15. Risk Register

### Risk 1 — Accidental asset purge

**Failure mode:** An operator misconfigures `retention_days = 7` instead of `retention_days = 70`. After 7 days, all episode assets are purged. The factory cannot re-run episodes because the source material is gone. The composite videos cannot be reproduced exactly.

**Mitigation:** The 48-hour purge grace period (§8.2) gives a window to catch and cancel a misconfigured purge. The Dashboard shows the scheduled purge queue with the grace period countdown — the operator can see what will be purged and when. The purge intent is logged and the operator is notified via OIS when a large-volume purge is scheduled (Asset Governance emits a `large_purge_scheduled` signal to OIS when a single schedule would purge more than 10 episodes' assets). Configuration changes to `retention_days` require Admin authority and show a preview of which episodes would be affected before the save is confirmed.

---

### Risk 2 — Archive reuse of outdated assets

**Failure mode:** A scene video was produced under the old color palette (before the channel updated from warm tones to cooler tones). It is reused in a new episode. The BGA gate passes because the BGA config was not updated to reflect the palette change. The published episode has visually inconsistent scenes.

**Mitigation:** `bga_config_version` is tracked on every VerificationRecord. When the channel's BGA configuration changes (brand rule update, palette change), all archived assets with an older `bga_config_version` are marked `needs_reverification`. They cannot be reused until reverification passes. If the BGA config version change is detected during a lookup, the lookup result includes `requires_reverification: true` and does not provide the asset URI — preventing reuse without re-evaluation.

---

### Risk 3 — Cross-channel asset leakage

**Failure mode:** A factory manages two competitor channels in the same niche. Cross-channel reuse is enabled for cost efficiency. Channel A's visual assets appear in Channel B's episodes. The two channels' aesthetics become indistinguishable.

**Mitigation:** Cross-channel reuse requires explicit opt-in per channel (`allow_cross_channel_reuse = true`). It is disabled by default. For client channels, cross-channel reuse is blocked entirely unless the factory admin has explicitly enabled it AND both client contracts permit shared assets. The archive lookup trace (§11.3) records which assets came from cross-channel reuse, making the dependency visible and auditable.

---

### Risk 4 — Storage cost growth without visibility

**Failure mode:** A factory accumulates 2 TB of video assets over 6 months. Storage costs are $200/month. The operator has no budget set for storage and doesn't notice the growing cost.

**Mitigation:** Storage costs are tracked in the `storage_cost` category of the Cost Ledger and included in the Budget Governance dashboard. The Archive Metrics dashboard (§11.1) shows total storage by tier and estimated daily cost. The Learning Module's Cost Intelligence Agent monitors storage cost trends and will generate an `efficiency_signal` if storage cost exceeds 15% of total production cost — surfacing the growth before it becomes significant.

---

### Risk 5 — Cold tier retrieval blocks production

**Failure mode:** A scene asset needs reverification. The asset is in cold storage (Glacier). Retrieval takes 4 hours. The run stalls waiting for the retrieval. The episode production is 4 hours late.

**Mitigation:** Cold tier retrieval latency is surfaced in the `ArchiveLookupResult.retrieval_latency_estimate_seconds`. The run coordinator (Run OS) checks this value before committing to the archive reuse. If the latency exceeds the run's time tolerance, the run generates a new asset instead of waiting. Cold retrieval is never used as a blocking operation without the run coordinator's explicit decision. The configurable threshold for cold retrieval tolerance is set per channel in archive settings (default: do not use cold retrieval if latency > 30 minutes).

---

### Risk 6 — Archive lookup produces wrong asset at high similarity

**Failure mode:** Scene description A is 88% similar to scene description B (just above the threshold). The archive returns the asset for B when A is requested. The visual is close but wrong — a different underground space than the script describes.

**Mitigation:** Similarity thresholds (§5.3) are set conservatively (0.85–0.90 depending on type). The generating parameters used for the lookup include the specific scene description hash — not just the style parameters. A hash match requires the scene content to be nearly identical, not just the style. The similarity score reflects both parameter and content hash distance. Operators can increase the similarity threshold in archive settings if they find false matches are occurring (at the cost of lower hit rate).

---

### Risk 7 — Archive polluted by failed assets being reused

**Failure mode:** `retain_raw_assets = true`. A scene video failed the BGA gate (wrong color palette). It is retained but marked `quality_status: failed`. An archive lookup retrieves it anyway because the similarity was high and the lookup didn't check quality status.

**Mitigation:** Archive lookup (§5.2) explicitly checks `quality_status`. Any asset where `quality_status = failed` or `quality_status = needs_reverification` is excluded from the lookup result — the lookup returns `hit: false` even if the asset exists. Failed assets are never served as archive reuse candidates regardless of similarity score.

---

### Risk 8 — Purge of assets before analytics are linked

**Failure mode:** An episode is published. Assets are purged 7 days later (retention_days = 7). The YouTube analytics for this episode are ingested at day 8 (post-stabilization). The Learning Module tries to correlate scene assets with retention metrics to identify which visual approach drove higher retention. The assets are gone.

**Mitigation:** Assets for published episodes are not purged until the platform analytics stabilization window has elapsed and the analytics have been ingested for that episode (confirmed by Analytics Layer). The purge eligibility check (§8.1) includes a guard: `episode.analytics_stabilized = true` must be set before episode assets are eligible for purge. For episodes on platforms with long stabilization windows (YouTube: 48h minimum, but 7 days for more stable retention data), purge is delayed accordingly.
