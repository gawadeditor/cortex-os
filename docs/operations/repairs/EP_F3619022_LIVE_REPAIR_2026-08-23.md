## 4. The live PUT — first attempt failed closed, root cause fixed, retried

**First attempt** (all 4 posts): `repair_existing_post()` reported
`status: "ambiguous"` for every post — correctly, never a false success.
A direct diagnostic PUT against the real API isolated the cause: **HTTP
400**, `"Invalid input: expected string, received object"`,
`param: "platforms.0.accountId"`. Zernio's `GET` returns
`platforms[].accountId` as an **expanded object**
(`{_id, platform, profileId, displayName, ...}`); `PUT` requires the
**plain id string** for the same field — a real, previously-unknown
contract asymmetry. Zero ledger rows were touched by this failed
attempt (no platform had a `to_submit` guard action, since youtube was
already locally `succeeded` for all four deliverables).

**Fix**: `ZernioProvider.repair_existing_post()` and
`build_proposed_update_body()` now normalize `accountId` to its plain id
string on every existing entry before sending — every *other* field
(`platformSpecificData`, `contentHash`, provider `_id`, `status`,
`publishAttempts`, `profileId`, `customMedia`, `scheduledFor`) is still
carried through completely untouched.

**Second attempt** (informed retry, not blind — root cause diagnosed and
fixed first, per the reconciliation discipline): all 4 posts returned
`status: "content_corrected"` (HTTP 200, valid `post` envelope).
